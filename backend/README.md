# Sohastics — Backend

REST API, database, authentication, media storage and the admin panel for the Sohastics website.
The public website lives in `../frontend` and is unchanged visually; it now reads all of its content
from this backend and sends the contact form, reviews and analytics to it.

- **Runtime:** Node.js 22.13+ (uses the built-in `node:sqlite`; **no npm dependencies to install**)
- **Database:** SQLite (single file, WAL mode, versioned migrations)
- **Auth:** scrypt-hashed passwords, signed session cookie (HttpOnly), CSRF guard, rate limits, account lockout
- **Admin panel:** `/admin/` (served by this backend, separate from the public site)

---

## 1. Folder structure

```
project-root/
├── frontend/                 public website (HTML/CSS/JS) — talks to the API, no secrets inside
│   └── js/api-config.js      where the API lives (CMS_API_BASE)
└── backend/
    ├── src/
    │   ├── server.js         start-up, housekeeping, graceful shutdown
    │   ├── app.js            middleware pipeline, static serving
    │   ├── config/           environment → typed config
    │   ├── routes/           every URL → controller (public / auth / admin)
    │   ├── controllers/      HTTP layer: validate input, call services, shape responses
    │   ├── services/         business logic (content, media, auth, analytics, dashboard, seeding)
    │   ├── models/           SQL access (db.js holds the schema migrations)
    │   ├── middleware/       security headers, CORS, auth, rate limit, body parsing, static files, errors
    │   └── utils/            router, validation, sanitising, JWT, password hashing, multipart, logger
    ├── admin/                admin panel (HTML/CSS/JS), served at /admin/
    ├── database/             SQLite file lives here (git-ignored) + defaults.json (first-run content)
    ├── uploads/              uploaded images/videos (git-ignored), served at /uploads/
    ├── scripts/              init-env, setup-db, create-admin
    ├── tests/                automated tests (node:test)
    ├── .env.example
    └── package.json
```

## 2. Installation

```bash
cd backend
npm run init          # creates .env with a freshly generated JWT_SECRET
```

There is nothing to `npm install` — the backend has no runtime dependencies. (`npm install` is harmless if you run it.)

## 3. Environment variables (`.env`)

| Variable | Purpose | Default |
|---|---|---|
| `NODE_ENV` | `development` or `production` | `development` |
| `PORT`, `HOST` | listen address | `3000`, `0.0.0.0` |
| `FRONTEND_URL` | origin the website is served from (CORS, links) | `http://localhost:PORT` |
| `CORS_ORIGINS` | extra allowed origins, comma separated | — |
| `SERVE_FRONTEND` / `FRONTEND_DIR` | let this server also serve `../frontend` | `true` / `../frontend` |
| `DATABASE_URL` | SQLite file, e.g. `file:./database/sohastics.sqlite` | as shown |
| `UPLOAD_DIR` | where uploads are stored | `./uploads` |
| `PUBLIC_URL` | prefix for uploaded-file URLs if the API is on its own domain | — |
| `JWT_SECRET` | **required in production**, 32+ random characters | generated by `npm run init` |
| `SESSION_HOURS` | admin session length | `12` |
| `COOKIE_SAMESITE`, `COOKIE_SECURE` | session cookie flags (`Secure` is automatic in production) | `Lax` |
| `TRUST_PROXY` | set `true` behind nginx/a load balancer so real client IPs are used | `false` |
| `SEED_DEFAULTS` | fill an empty database with the site's original text on first start | `true` |
| `MAX_IMAGE_MB`, `MAX_VIDEO_MB` | upload limits | `8`, `100` |
| `RATE_LIMIT_ENABLED` | turn rate limiting on/off | `true` |
| `ADMIN_EMAIL`, `ADMIN_USERNAME`, `ADMIN_PASSWORD` | optional: create the first admin automatically on start (remove the password afterwards) | — |

`.env` is git-ignored. Never commit it.

## 4. Database setup

```bash
npm run db:setup      # creates database/sohastics.sqlite and applies all migrations (idempotent)
```

The server also applies pending migrations on every start, and on the very first start loads the
website's original text (`database/defaults.json`) so the site looks exactly as before until you edit it.

Tables: `admins`, `site_content` (theme, page text, contact info, SEO, page visibility, photos),
`projects`, `services`, `websites`, `awards`, `milestones`, `skills`, `reviews`, `messages`, `media`,
`activity_logs`, `analytics_events`, `analytics_heartbeats`, `revoked_tokens`, `schema_migrations` — with ids, timestamps,
status columns and indexes on the columns used for sorting and filtering.

## 5. Admin setup

```bash
npm run admin:create
# or non-interactive:
ADMIN_EMAIL=you@example.com ADMIN_USERNAME=you ADMIN_PASSWORD='a-long-passphrase-9' npm run admin:create
```

Passwords need 10+ characters with letters and numbers. There is **no default password**.
Running the command again for an existing admin resets that admin's password.

## 7. Connecting the frontend

- **Same server (default):** `SERVE_FRONTEND=true` — the site and API share one origin; nothing to configure.
- **Frontend hosted elsewhere** (Netlify, static host, CDN):
  1. Edit `frontend/js/api-config.js`: `window.CMS_API_BASE = 'https://api.example.com';`
  2. In `backend/.env`: `FRONTEND_URL=https://www.example.com`, `PUBLIC_URL=https://api.example.com`, `SERVE_FRONTEND=false`.
  3. The admin panel stays on the API domain (`https://api.example.com/admin/`), so its session cookie is first-party.

The frontend never sees database credentials or secrets; public pages only read published content and submit forms.

## 8. API

All responses share one shape:

```json
{ "success": true,  "message": "Message received", "data": { } }
{ "success": false, "message": "Please correct the highlighted fields", "error": "VALIDATION_ERROR", "errors": [{ "field": "email", "message": "Enter a valid email address" }] }
```

Lists add `"meta": { "page", "limit", "total", "pages" }`. Server errors never expose internals.

### Public (no sign-in)

| Method | Path | Notes |
|---|---|---|
| GET | `/api/health` | status and upload limits |
| GET | `/api/content` | all published site content (ETag cached); `/api/content/version` is a cheap change check |
| GET | `/api/settings` | theme, page text, contact info, SEO, page visibility |
| GET | `/api/projects` · `/api/projects/:id` | also `websites`, `services`, `awards`, `milestones`, `skills`; supports `page`, `limit` |
| GET | `/api/testimonials` | approved reviews only |
| POST | `/api/messages` | contact form → stored as **unread** with a unique id; validated, sanitised, rate limited (5/hour/IP), honeypot |
| POST | `/api/reviews` | visitor review → stored **pending** until approved |
| POST | `/api/analytics/event` · `/api/analytics/heartbeat` | page views and live-visitor pings |

### Authentication

| Method | Path | Notes |
|---|---|---|
| POST | `/api/auth/login` | `{ identifier, password }` (username or email); 10 attempts / 15 min / IP, lockout after repeated failures |
| POST | `/api/auth/logout` | ends the session server-side |
| GET | `/api/auth/me` | current admin |
| POST | `/api/auth/change-password` | needs current password; signs out other sessions |
| PATCH | `/api/auth/profile` | name / email / username (needs current password) |

### Admin (`/api/admin/…`, session cookie required)

| Area | Endpoints |
|---|---|
| Dashboard | `GET /dashboard` (counts, recent projects/inquiries/activity), `GET /system` |
| Content | `GET /content`, `PUT /content/:key` (theme, content, contactInfo, images, pages, seo, and the list keys) |
| Projects, services, websites, awards, milestones, skills | `GET /<name>`, `POST /<name>`, `GET/PUT/DELETE /<name>/:id`, `PUT /<name>/reorder` |
| Messages | `GET /messages` (`q`, `status`, `projectType`, `page`, `limit`), `GET /messages/stats`, `GET/PATCH/DELETE /messages/:id`, `POST /messages/mark-all-read`, `DELETE /messages?confirm=all` |
| Testimonials | `GET /reviews`, `PATCH /reviews/:id` (`approved`), `DELETE /reviews/:id` |
| Media | `GET /media`, `POST /media` (multipart `file`), `DELETE /media/:id` (`?force=1` if still in use) |
| Analytics | `GET /analytics?days=`, `GET /analytics/live`, `DELETE /analytics` |
| Activity | `GET /activity` (`action`, `page`, `limit`) |

Writes from the browser must send `X-Requested-With` (the bundled clients do) and come from an allowed origin.

## 9. Production deployment

1. Install Node 22.13+ on the server, copy `backend/` and `frontend/` (keep them side by side).
2. `npm run init`, then edit `.env`: `NODE_ENV=production`, `FRONTEND_URL=https://your-domain`, `TRUST_PROXY=true`.
3. `npm run db:setup && npm run admin:create`.
4. Run it under a process manager, e.g. systemd:
   ```ini
   [Service]
   WorkingDirectory=/srv/sohastics/backend
   ExecStart=/usr/bin/node src/server.js
   Restart=always
   User=sohastics
   ```
5. Put nginx (or Caddy) in front for HTTPS; proxy to `127.0.0.1:3000` and pass `X-Forwarded-For` / `X-Forwarded-Proto`. Set `client_max_body_size 110m;` so video uploads fit.
6. **Back up** `database/sohastics.sqlite` (use `sqlite3 … ".backup"` while running) and the `uploads/` folder.
7. In the admin panel: Settings → set your real site URL under SEO, then upload the generated `sitemap.xml` / `robots.txt`.

## 10. Security notes

- Passwords: scrypt with per-user salt; never stored or logged in plain text. Failed logins are rate limited and lock the account temporarily.
- Sessions: signed token in an `HttpOnly`, `SameSite` cookie (`Secure` in production); changing the password or signing out invalidates it server-side.
- CSRF: cookie-authenticated writes require a custom header **and** an allowed `Origin`.
- Input: every field validated and sanitised (control characters and HTML tags stripped from visitor text); URLs in content must be `http(s)`/`mailto`/`tel`/relative — `javascript:` is rejected.
- Uploads: file type is detected from the file's actual bytes (name and declared type ignored); only PNG/JPG/GIF/WebP and MP4/WebM/MOV; SVG and anything executable are rejected; size limits; random UUID filenames; stored under `uploads/` and served with `nosniff`.
- Headers: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, COOP, HSTS in production, strict CSP on API responses.
- Secrets live only in `.env` (git-ignored). `.env.example` contains placeholders.
- Known limits: rate-limit counters are in memory (reset on restart; use the proxy for stronger limits on multi-instance setups); static HTML pages are served without a CSP because the site uses inline theme scripts; uploaded images are stored as received (the admin panel already resizes photos in the browser before upload) — there is no server-side re-encoding.
